# Portfolio Design System

You are working on a professional personal portfolio website.

This skill is the PROJECT-SPECIFIC DESIGN AUTHORITY.

Use `design-taste-frontend` for general frontend design intelligence,
but use this skill for project-specific decisions.

If this skill conflicts with generic design recommendations,
FOLLOW THIS SKILL.

---

# 1. PRIMARY OBJECTIVE

The portfolio must communicate:

- professional credibility
- technical competence
- design awareness
- clarity
- intentionality
- modern frontend craftsmanship

The website must feel designed by a real developer/designer,
not generated from a generic AI website template.

Prioritize:

1. readability
2. information hierarchy
3. project storytelling
4. visual consistency
5. responsive usability
6. performance
7. accessibility
8. subtle visual personality

Never sacrifice usability for visual effects.

---

# 2. DESIGN PERSONALITY

Target visual direction:

- modern
- editorial
- premium
- minimal
- technical
- sophisticated
- confident
- clean

The visual identity should sit between:

Editorial Portfolio
+
Modern Developer Portfolio
+
Digital Product Case Study

Do NOT turn the website into:

- generic SaaS landing page
- startup template
- gaming website
- cyberpunk interface
- overly futuristic portfolio
- Dribbble concept with poor usability

---

# 3. ANTI GENERIC-AI DESIGN RULES

Actively avoid common AI-generated website patterns.

DO NOT automatically use:

- gradient text
- purple/blue gradients
- excessive glassmorphism
- glowing borders
- floating gradient blobs
- excessive rounded cards
- excessive pill-shaped containers
- giant centered hero text everywhere
- identical card grids in every section
- random decorative icons
- unnecessary badges
- excessive shadows
- excessive animations
- meaningless statistics
- fake testimonials
- fake clients
- fake achievements
- fake metrics

Every visual element must have a reason to exist.

If removing an element improves clarity, remove it.

---

# 4. VISUAL HIERARCHY

Every section must have a clear hierarchy.

Recommended hierarchy:

Eyebrow / metadata
↓
Primary heading
↓
Supporting description
↓
Primary content
↓
Secondary information
↓
CTA

Do not make every text element visually important.

There must be obvious distinction between:

- display heading
- section heading
- project title
- body copy
- metadata
- labels
- captions

---

# 5. TYPOGRAPHY

Typography is a major visual component.

Prioritize:

- strong contrast between display and body text
- readable body sizes
- controlled line length
- intentional letter spacing
- consistent hierarchy

Body text should generally remain around:

60–75 characters per line.

Avoid:

- extremely thin text
- tiny body text
- excessive uppercase paragraphs
- low contrast text
- decorative fonts for long content
- too many font families

Use uppercase primarily for:

- metadata
- category labels
- small navigation labels
- project numbers

Never sacrifice readability for aesthetics.

---

# 6. SPACING SYSTEM

Whitespace must feel intentional.

Use consistent spacing relationships.

Prefer spacing based on a predictable scale such as:

4
8
12
16
24
32
48
64
80
96
128

Do not randomly choose spacing values.

Sections should have enough breathing room,
but avoid unnecessary giant empty areas.

Desktop sections may use generous whitespace.

Mobile layouts should be more compact.

---

# 7. GRID & LAYOUT

Avoid making every section use the same composition.

Use variation intentionally.

Possible layouts:

- asymmetric editorial grid
- split layouts
- image + content compositions
- controlled full-width sections
- horizontal project showcases
- structured case-study layouts

Prefer asymmetry when it improves visual interest.

Do not force symmetry everywhere.

Maintain strong alignment between elements.

---

# 8. HERO SECTION

The hero must immediately answer:

WHO IS THIS?
WHAT DOES HE DO?
WHY SHOULD I KEEP LOOKING?

Avoid unnecessary marketing language.

Hero should prioritize:

- name / identity
- role
- short positioning statement
- primary CTA
- secondary CTA when necessary

Do not overload the hero with:

- many badges
- skill icons
- fake metrics
- long biography
- excessive visual effects

The hero should feel confident and intentional.

---

# 9. ABOUT SECTION

Do not make About a giant autobiography.

Focus on:

- professional direction
- approach to building products
- relevant technical/design interests
- concise personality

Use short paragraphs with good readability.

---

# 10. SKILLS

Skills must communicate actual capabilities.

Avoid generic progress bars such as:

HTML 95%
CSS 90%
JavaScript 85%

Unless backed by meaningful evaluation,
percentage-based skill indicators should not be used.

Prefer:

- categorized skills
- technology groups
- capability descriptions
- contextual examples

Example:

Frontend
React · Next.js · TypeScript · Tailwind

Backend
Laravel · PHP · REST API

Database
MySQL · MariaDB

Design
UI/UX · Figma · Responsive Design

---

# 11. PROJECT SECTION

PROJECTS ARE THE MOST IMPORTANT CONTENT.

Prioritize them visually.

Each project should clearly communicate:

Project Name

Role

Problem / Context

Contribution

Technology

Result / Outcome

Visual Preview

CTA

Do not hide project information behind excessive interaction.

Important information must remain discoverable.

Project screenshots should be treated as editorial content,
not decoration.

Avoid tiny screenshots.

Give important projects visual space.

---

# 12. PROJECT STORYTELLING

Use this storytelling structure when appropriate:

CONTEXT
↓
PROBLEM
↓
ROLE
↓
PROCESS / IMPLEMENTATION
↓
SOLUTION
↓
RESULT

Do not fabricate results.

If no measurable result exists,
describe the functional or learning outcome instead.

---

# 13. PROJECT ROLE CLARITY

Make individual contribution obvious.

Examples:

Fullstack Developer

UI/UX Designer

Frontend Developer

Do not imply team responsibilities that were not actually performed.

---

# 14. PROJECT SCREENSHOTS

Screenshots should:

- remain readable
- preserve aspect ratio
- have intentional cropping
- support project storytelling
- work responsively

Avoid:

- random perspective transforms
- excessive 3D mockups
- heavy shadows
- tiny screenshots
- screenshots purely used as background texture

For UI/UX projects, visual work should receive high prominence.

---

# 15. CARDS

Do not automatically wrap everything inside cards.

A container should exist only when grouping is useful.

If cards are used:

- keep border radius controlled
- avoid excessive shadow
- maintain strong spacing
- preserve visual hierarchy

Editorial borders and whitespace are preferred over heavy shadows.

---

# 16. COLOR

Use the project's existing color system.

Do NOT introduce random new colors.

Colors must have defined responsibilities:

Primary
Secondary
Background
Surface
Text Primary
Text Secondary
Border
Accent

Maintain sufficient contrast.

Avoid low-contrast decorative text.

Accent colors should guide attention,
not dominate the interface.

---

# 17. DARK MODE

If the project already supports dark mode,
maintain visual parity.

Do not introduce dark mode unless explicitly requested.

Dark mode should not simply invert colors.

Check:

- contrast
- borders
- images
- surfaces
- hover states
- muted text

---

# 18. BUTTONS & CTA

Maintain clear CTA hierarchy.

PRIMARY CTA:
highest visual priority.

SECONDARY CTA:
visible but quieter.

TERTIARY:
text/link treatment.

Avoid having multiple buttons competing equally.

Button labels should describe the action.

Prefer:

View Project
View Case Study
GitHub
Download CV
Contact

instead of vague labels such as:

Learn More

---

# 19. MOTION

Motion must support comprehension.

Use animation for:

- entrance hierarchy
- transitions
- interaction feedback
- storytelling
- state changes

Avoid animation for decoration alone.

Preferred:

- subtle fade
- controlled translate
- stagger
- restrained hover interaction

Avoid:

- excessive parallax
- constant floating objects
- aggressive scaling
- unnecessary rotating elements
- animation on every text element

Animations must remain smooth.

Respect:

prefers-reduced-motion

where appropriate.

---

# 20. RESPONSIVE DESIGN

Responsive behavior is mandatory.

Never treat mobile as a scaled-down desktop.

Review at minimum:

Mobile
~320–430px

Tablet
~768–1024px

Desktop
~1280px+

Large Desktop
~1440px+

Check:

- typography
- navigation
- image cropping
- section spacing
- project layouts
- CTA accessibility
- horizontal overflow
- touch targets

Mobile content priority should remain clear.

---

# 21. MOBILE UX

Mobile should prioritize:

1. identity
2. project discovery
3. readability
4. contact action

Avoid giant mobile hero sections.

Avoid excessive vertical gaps.

Touch targets should generally be at least ~44px.

Never require hover to access important information.

---

# 22. ACCESSIBILITY

Maintain:

- semantic HTML
- keyboard navigation
- visible focus states
- descriptive alt text
- appropriate ARIA when needed
- sufficient contrast
- logical heading hierarchy

Do not remove focus outlines without providing a replacement.

---

# 23. FRONTEND ENGINEERING

Design improvements must not damage architecture.

Preserve:

- reusable components
- TypeScript safety
- existing routes
- data structures
- SEO
- accessibility
- performance

Avoid unnecessary dependencies.

Before installing a library,
check whether the existing stack can solve the problem.

---

# 24. PERFORMANCE

Visual quality must not destroy performance.

Optimize:

- images
- fonts
- animation
- client components
- bundle size

Avoid unnecessary JavaScript.

For Next.js projects:

prefer server components unless client behavior is required.

Use Next/Image appropriately.

Avoid layout shift.

---

# 25. EXISTING DESIGN PROTECTION

When asked to improve one section:

DO NOT redesign unrelated sections.

First inspect:

- existing components
- design tokens
- typography
- spacing
- responsive behavior
- existing patterns

Then make targeted improvements.

Preserve good existing decisions.

---

# 26. REDESIGN PROTOCOL

Before redesigning:

STEP 1
Inspect the current implementation.

STEP 2
Identify concrete design problems.

STEP 3
Separate functional problems from visual problems.

STEP 4
Determine what should remain unchanged.

STEP 5
Implement the smallest meaningful design improvement.

STEP 6
Review responsive behavior.

STEP 7
Check visual consistency with surrounding sections.

Never redesign blindly.

---

# 27. CONTENT INTEGRITY

Never invent:

- clients
- companies
- testimonials
- employment
- awards
- metrics
- certifications
- user numbers

Use only content available in the project or explicitly supplied.

If information is missing,
design around the missing information instead of fabricating it.

---

# 28. UI REVIEW CHECKLIST

Before considering a UI task complete, verify:

[ ] Visual hierarchy is clear
[ ] Body text is readable
[ ] Contrast is sufficient
[ ] Spacing is consistent
[ ] Alignment is intentional
[ ] Mobile layout works
[ ] Tablet layout works
[ ] Desktop layout works
[ ] Images are correctly cropped
[ ] No horizontal overflow
[ ] Buttons have clear hierarchy
[ ] Hover states work
[ ] Focus states work
[ ] Animations are restrained
[ ] No fake content was introduced
[ ] Existing functionality still works
[ ] No unnecessary dependency was added

---

# 29. FINAL DESIGN QUESTION

Before finalizing any design decision ask:

Does this improve:

clarity,
hierarchy,
usability,
storytelling,
or brand identity?

If the answer is no,
the design element probably does not need to exist.

---

# 30. SKILL PRIORITY

When multiple skills are available:

1. portfolio-design-system
2. design-taste-frontend
3. general model design knowledge

Use `design-taste-frontend` to enhance decisions,
not to override this project's established visual identity.

The final interface should feel intentional,
cohesive, professional, and human-designed.
